1.0.0-beta.14.1 (patch on the 1.0.0-beta.14 line). IndexedDB fallback: snapshots saved from two tabs can no longer overwrite each other out of order, and `ensureDurable()` no longer resolves for a write that was lost. Every tab persists the same leader-owned SQLite database, but each tab's save was an unconditional put, so a follower's snapshot taken earlier could reach IndexedDB after a newer one and replace it; a write whose `ensureDurable()` (or `flushPersistence()`) had already resolved was then missing after a reload.

- Every in-memory worker database is a lineage: when it starts (first open, reload, leader promotion), one IndexedDB `readwrite` transaction claims an epoch higher than every earlier one, reads the snapshot it restores from, and stores a fence version for it. A commit counter in the database counts its write transactions and is read in the same transaction as the snapshot data.
- Saves are a compare-and-put: one IndexedDB `readwrite` transaction stores the JSON dump, the binary image and the version together only when the snapshot is newer. A snapshot the stored one already covers is skipped. One from a replaced worker database (taken before a leader change, or before the database was deleted) is refused with a `PersistenceError` whose `context.code` is `SNAPSHOT_SUPERSEDED`, reported on `store:persistence-error` with `code: 'SNAPSHOT_SUPERSEDED'`.
- `ensureDurable()` is tied to the worker database each write was made in. It resolves only when a saved snapshot of that database holds the write (a save by another tab counts). When that database was replaced before such a snapshot was saved, the write is gone and the barrier rejects with `SNAPSHOT_SUPERSEDED` instead of resolving on the new database's snapshot.
- A snapshot transaction that aborts at commit (for example a quota failure while writing to disk) now rejects with a `PersistenceError` instead of leaving later flushes and barriers waiting forever.
- Deleting the database keeps its epoch counter, so a tab that resumes after the delete can never save over a recreated database.
- A lost write stays lost: every later `ensureDurable()` rejects with `SNAPSHOT_SUPERSEDED` (it still covers that write) until `IndexedDbAdapter.acknowledgeLostWrites()` is called, instead of only the first one.
- A write and its commit count run in one transaction span pinned to one worker database. A storage leader change in between fails the call with a retriable `BridgeTerminatedError` (the span's leader-epoch binding from the multi-tab transaction isolation fix) instead of counting the write under the new leader's database.

Tabs still running an earlier release during an upgrade: versioned snapshots are stored under new keys (`<db>::v2::dump`, `<db>::v2::data`, `<db>::v2::version`) that earlier releases never write, so their unconditional saves can no longer overwrite them. Each save also writes the legacy keys (`<db>`, `<db>::dump`) as a mirror stamped with its version, so an earlier release restores the latest data. When a new copy of the database starts (reload, leader promotion), the two copies are reconciled by what can be proven: the legacy copy is used when it holds every operation of the versioned one (an earlier release saved later), the versioned one when it holds every operation of the legacy copy, and when each holds operations the other lacks (or the legacy copy is a database an earlier release deleted and created again), one is restored and the other is kept aside under `<db>::v2::preserved::<id>`, never deleted, and reported on `store:persistence-error` with `code: 'SNAPSHOT_DIVERGED'` (`IndexedDbAdapter.preservedSnapshots()` lists them). A database an earlier release deleted is not brought back from the new keys. A worker database an earlier release opened is saved to the legacy keys only. Snapshots written by earlier releases (legacy keys only) load as before and move to the new keys on the next save. OPFS and native SQLite storage are unchanged.
