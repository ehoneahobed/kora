IndexedDB fallback: snapshots saved from two tabs can no longer overwrite each other out of order. Every tab persists the same leader-owned SQLite database, but each tab's save was an unconditional put, so a follower's snapshot taken earlier could reach IndexedDB after a newer one and replace it; a write whose `ensureDurable()` (or `flushPersistence()`) had already resolved was then missing after a reload. A snapshot now carries a version (the worker database it was read from and a counter of the write transactions committed in it, read in the same transaction as the data) and is saved with a compare-and-put: one IndexedDB `readwrite` transaction reads the stored version and writes the JSON dump, the binary image and the version together only when the snapshot is newer. A snapshot the stored one already covers is skipped, and one from an older worker database (taken before a leader change) is refused with a `PersistenceError` (`SNAPSHOT_SUPERSEDED`, reported through `store:persistence-error`). The binary image and the dump are always stored and restored as one snapshot. Snapshots written by earlier releases (no version) load as before and are replaced by the next save; a worker database opened by an earlier release in another tab is versioned on its first save from this release. OPFS and native SQLite storage are unchanged.
