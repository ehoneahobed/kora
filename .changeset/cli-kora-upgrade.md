New `kora upgrade` (D2): bumps every Kora package in a project (`korajs`, `@korajs/*`) to one version, so versions never drift apart. It detects the package manager (the `packageManager` field, else the lockfile), finds the specifiers in `dependencies`, `devDependencies`, `optionalDependencies`, `overrides`, `pnpm.overrides`, `resolutions` and a `pnpm-workspace.yaml` `catalog`/`catalogs`/`overrides`, resolves a target (`--tag latest|beta|canary`, default `beta` for a project on a prerelease, or an exact `--to <version>`; every package must resolve to the same version), and rewrites each specifier in its own `^` / `~` / exact style while keeping the file's formatting. `--dry-run` prints the plan and diagnostics and changes nothing; `--yes` skips the confirmation (a non-interactive shell without it refuses); a downgrade needs `--allow-downgrade`. After rewriting it runs the package manager's install, then `kora doctor --skip-network` from the upgraded CLI, and exits non-zero with a clear message if either fails. Lockfiles and `node_modules` are never edited directly.

A small codemod registry (`src/upgrade/codemods/`, interface `Codemod`) reports what a release changed in your source. The first three are report-only diagnostics with documentation links: removed or no-longer-negotiated protobuf serializers (`wire-format-serializers`), `t.json()` / `t.object()` values written or read as JSON strings (`json-field-string-values`, pointing at `findJsonStringValues`), and null tests on fields that now read their schema default on the server (`defaulted-field-null-checks`). `--apply-codemods` applies edits a codemod marks safe; none of the built-in ones rewrite code.
