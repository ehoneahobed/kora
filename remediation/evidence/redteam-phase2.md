## What held up

- **Upload ordering vs ack (attacked first).** I tried to make the ack of a timestamp-ordered batch cover an unprocessed op. The setup was two tabs on one node with skewed HLCs, plus a transient validator throw. It is closed, because `sendUpload` sorts each batch by `(node, seq)` (`compareForUpload`), and acks resolve only the named batch.
- **Exactly-once atomic increments.** Increments stayed exactly-once under 20% drop, duplicate and reorder, with prefix resets (simulated upgrade re-uploads) mid-run. All replicas and the server matched the issued total (4 seeds). Pending counts drain once the network calms.
- **No-silent-loss invariants.** The U (prefix), D (watermark) and C (convergence) invariants held on 8 extra seeds (101..808).
- **Mixed versions, Phase 2 clients on a beta.13 server.** These converged with no loss under chaos (4 seeds).
- **Mixed versions, beta.13 clients on the Phase 2 server.** One seed out of five lost a beta.13 op. beta.13 clients lose ops under chaos against the beta.13 server too (SYNC-4 class, fixed by upgrading the client), so this is not attributed to Phase 2 server code.
- **Dedup before auth (RT-31).** It is not a bypass. The own-node fast path requires the stored op to be under the session's own claimed node. A foreign op is acked only for the exact stored `(node, seq, id)`, which needs a 256-bit id from outside the attacker's scope.
  - Caveat: the server never checks `id == hash(content)`, so content addressing is client-trusted. No exploit was found, but it should be verified at ingest.
- **Accepted-scope resume (RT-33).** A forged `acceptedScopeKey` or watermark can only make the forging client skip part of its own stream, or restart it. Filtering always uses the scope resolved now, and a watermark above the frontier resets to 0. There is no disclosure and no skip for others.
- **`SEQUENCE_CONFLICT` cannot be used against another device.** That would require uploading under its node, which the node claims refuse. Outside RT-37, conflicts arise only from the device's own state (RT-35).
- **Legacy duplicate pairs.**
  - A second op delivered to a client under an occupied `(node, seq)` goes to `_kora_seq_conflicts` and still folds.
  - A renumbered own op is acked as a duplicate.
  - The epoch logic and the partial index behave on Postgres 16 (`sequence-enforcement-epoch.test.ts`, `ingest-integrity.test.ts`: 23/23 with `KORA_PG_TEST_URL`).
- **Legacy-pool migration.** sqlite-wasm's `importDb` associates the file name only after all bytes are written, so a page killed mid-copy leaves no half database under the name. The legacy copy is unlinked only after `quick_check` on the import.
- **Backpressure and liveness.** The delivery stream polls `bufferedAmount` on WS and HTTP, and any inbound message (delivery acks) counts as liveness for the server ping. No busy-client kill was found by reading the code; it was not run against a throttled link.
- **Phase 1 security fixes.** `scripts/remediation/check.mjs --all` (node, Postgres, Chromium) shows no regression of RT-1..RT-34.
- **Not attacked** (no time, or covered by existing W8a real-Chromium checks):
  - follower transaction during leader failover;
  - freeze/pagehide release;
  - `deleteDatabase` while another tab writes.

### What held up (round 2)

- **Lost-tail recovery is exactly-once.** The device lost three uploaded ops (an atomic increment, a delete and an update), then wrote four new ops offline, three of them reusing lost numbers. After sync, the device, a peer and the server all hold count 26 and the same notes, with 5 counter ops on the server, nothing pending and nothing rejected. This test is kept as a guard: `packages/test/tests/phase2-redteam-r2-guards.test.ts`.
- **Renumber on `SEQUENCE_CONFLICT`.**
  - No loop was found. Each recovery takes `floor = max(handshake own entry, op seq)`, and the handshake own entry is the server's true max (never scope-filtered: `msg.nodeId` is always visible).
  - Renumbering keeps the id. Postgres serializes appends under the delivery-counter lock and re-reads holders, so a concurrent re-upload of the same op is a duplicate, never a conflict. The server therefore never answers `SEQUENCE_CONFLICT` for an op it stores, and atomic increments are not double-applied.
  - A peer cannot trigger renumbering, because node claims confine uploads to the session's own node.
  - A delivery batch arriving after the in-session watermark reset is treated as a gap (not applied, not acked), so the next session's full resync from 0, own ops included, is what recovers.
- **Server behind, for a node that has ops in the backup.** It re-uploads once (`maxSubmissions` 1 in RT-45) and converges. The failure is only the absent-entry case (RT-45).
- **Legacy pairs on Postgres 16.** `legacy-sequence-and-ingest-budget.test.ts` and `sequence-enforcement-epoch.test.ts` pass (28/28). A new client that omits `sequenceReservation` can store a duplicate only under its own node. Receivers fold it through `_kora_seq_conflicts`, which harms nothing beyond RT-48 for vector clients.
- **Durability barrier.** Every upload path (streaming `sendUpload`, the initial delta, adoption and recovery sessions) goes through `markSent` then `ensureDurable`. `MergeAwareSyncStore` forwards every new store method. The generation-tracked IndexedDB barrier cannot be satisfied by a snapshot that predates the write.
- **Web Locks (real Chromium).** A frozen page (CDP `Page.setWebLifecycleState` frozen) keeps its node lock, so a frozen tab's node is not adopted; its writes wait and count as pending. Two tabs cannot adopt one node, because acquisition uses `ifAvailable`. A caveat for RT-40: `window.open` copies sessionStorage, so an opened tab shares its opener's per-tab node id (two live engines on one node). This was harmless in testing, because sequence numbers are reserved in a transaction in the shared database and uploads are deduplicated by id.
- **Chaos.** `chaos:nightly` passed: 10 clients × 1,000 ops, 10% drop, 5% duplicate. The no-silent-loss invariants held on 8 extra seeds, `test:release-gate` passed, and `check.mjs --all` (node, Postgres, Chromium, `LMS_OPS=20000`) shows no regression.
- **Not attacked:**
  - leader failover during an adoption;
  - IndexedDB fallback with several tabs (each tab has its own in-memory copy, a pre-existing W8a question);
  - the ingest limiter keyed per node, which an authenticated user can multiply by minting node ids (pre-existing, outside this round's mechanisms).

### What held up (round 3)

- **Resolutions cannot make the server skip an op it never stored, apart from RT-51.**
  - `ignored` and `refused` are recorded, and the write is awaited, before the answer is sent. Nothing is inserted for them, so a crash between the two leaves no half state.
  - `stored-elsewhere` is recorded only after the stored copy was found.
  - The resolved-through entry is used only in the handshake. The client never raises its acknowledged prefix from it; it raises only its sequence counter and runs one full resync. So a high resolution cannot hide a later unstored op. This holds even for a self-poisoned one, such as a refused op at seq 10^6 on the client's own node: that costs the device one counter raise and one full resync.
  - Resolution lookups are keyed by the session's own claimed node, so there is no oracle across devices or tenants.
  - The `op_id` primary key is global, so another node's row with the same id can pre-empt a record (`ON CONFLICT DO NOTHING`). That needs the victim's unstored op id, which is content-addressed and never disclosed. Keying the table by `(node_id, op_id)` would close the question.
- **Refused-id replay is the documented contract.** The docs say "`retriable: false`: retrying the same bytes will always fail" (`docs/guide/production-server.md`, `docs/api/server.md`). A fixed cause is answered with a NEW operation; no client API resubmits the same id.
  - Not documented: the server keeps refusals and validator `ignore` decisions forever. `operation_resolutions` therefore grows like the op log for apps that `ignore` high-volume writes. This needs a retention note, and backups do not carry the table.
- **`server-behind`: no false positive found.** The own entry is `max(stored max, resolved)`, read from committed state on every store (Postgres advances `sync_state` in the append transaction). It is never scope-filtered, and acks are sent only after the store write. Retriable rejections never advance the ack.
- **Clone detection does not duplicate stored ops.**
  - Setup: a cloned database, where copy A re-uploads a history of 2,101 increments from prefix 0 (a simulated upgrade, with a scan window of 2,000). A's new write collides above its handshake entry.
  - Result: clone detection fired and moved A to a fresh node. The counter stayed exactly 2,100 on both copies and on the server.
  - Why it holds: the upload queue is in causal (HLC) order, and the scan runs ahead of every flush. So by the time the colliding write is on the wire, every older own op is already flagged sent.
  - Cost 1: the abandoned node stays a local node of copy A, which adopts it and re-uploads the shared history once more, as duplicates.
  - Cost 2: on pinned and per-tab stores, the rotation throws `NODE_ID_PINNED` (reported as `NODE_ROTATION_FAILED`); the next session renumbers instead.
- **Degraded durability.**
  - Setup: the quota fails, and uploads proceed after 3 failed barriers (`sync:durability-degraded`, `DURABILITY_DEGRADED`). The device then crashes back to its last durable snapshot and writes 4 ops offline, 3 of them reusing lost numbers.
  - Result: one renumber per colliding write (3), with no storm and no duplicate. The server and peer counters are exact, and nothing is pending.
- **Adoption scheduler.** No starvation was found beyond RT-53, and no unbounded loop:
  - A parked node waits at most 1 h of backoff.
  - Causal cycles are broken in registry order.
  - A child whose parent is parked is adopted anyway, and parks again if it is deferred.
- **Principal binding.**
  - Post-fix databases behave correctly through sign-out, sign-in as another user and back, an offline switch, and the held-operations count (RT-42 repro, `phase2-node-fairness`). The exceptions are RT-50 (pre-fix databases) and RT-52 (in-flight reconnect).
  - With `namespaceByAuthUser: true`, a user switch without recreating the app keeps the first user's database, and the binding moves it to the new user's node. Nothing is uploaded as the wrong user, but the app must be recreated per user (`AuthBoundKoraProvider`).
- **Per-user ingest budget.** It is keyed by `userId`, like node claims, and `AuthContext` has no tenant notion, so the two are consistent. Anonymous principals get no user budget, so minting anonymous node ids still multiplies the per-node budget (pre-existing).
- **Seed 1117 invariant failure: a checker false positive, not a product bug.**
  - Device-0 held two updates that were later than another device's delete of the same record, so that delete lost the merge. By design, a losing delete is not logged.
  - The checker's `mergeKeptRecord` accepts such a delete only while the record still exists.
  - A second delete of the same record (delivery 42) then removed the record, so the earlier merge decision looked like a dropped op.
  - The replicas converged.
  - Fix the checker, for example by recognising the merge decision from the audit trace, so the nightly seeds stop being flaky.
- **Not attacked:**
  - leader failover during an adoption;
  - IndexedDB fallback with several tabs;
  - two live Postgres server instances, which were only reasoned from the code (one primary, and `sync_state` is written in the append transaction).
