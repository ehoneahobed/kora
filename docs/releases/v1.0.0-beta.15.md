# Kora.js 1.0.0-beta.15

> Released 2026-11-20. Checked against `main` on the day of the release (through #343), against the
> tag `v1.0.0-beta.14`: the 224 changesets added since beta.14. Each package's `CHANGELOG.md` has the
> per-change detail; this file is the narrative that goes with it. Section
> [Open items](#open-items-for-the-release) lists what is left for 1.0.

**Behaviour-changing, not protocol-breaking.** The sync protocol stays at version 2 (new handshake
and delivery fields are optional). Upgrade every `korajs` and `@korajs/*` package together, **sync
servers first, then clients**. `npx kora upgrade` does the version bump and runs `kora doctor`.
Desktop apps also rebuild with the updated Tauri plugin (its keychain support needs Rust 1.88 or
newer). Rolling back to beta.14 is not supported: see
[Rolling back](../guide/upgrading-to-beta15.md#rolling-back).

- **Security:** beta.15 fixes issues in published beta.14. See the
  [beta.14 security advisory](./security-advisory-beta15.md) ([GHSA-p6gp-vqp9-4hw4](https://github.com/ehoneahobed/kora/security/advisories/GHSA-p6gp-vqp9-4hw4)).

- Upgrade guide: [Upgrading to beta.15](../guide/upgrading-to-beta15.md), with the change each item
  needs, a checklist, and what to monitor.
- Coming from beta.12 or beta.13: read [Upgrading to beta.13](../guide/upgrading-to-beta13.md) first.

```bash
npx kora upgrade --to 1.0.0-beta.15   # or: pnpm add korajs@1.0.0-beta.15 @korajs/server@1.0.0-beta.15 ...
npx create-kora-app@beta my-app       # new apps
```

Every `korajs` and `@korajs/*` package is `1.0.0-beta.15`, except `@korajs/tauri`, which is on its own
version line: `0.5.0-beta.14` (a minor step for `deleteDatabase` and keychain storage). `create-kora-app`
is `0.1.25-beta.14`. New desktop apps pin `@korajs/tauri@0.5.0-beta.14`. `@korajs/spaces` is published
for the first time. All are prereleases on the `beta` dist-tag; `latest` also points at them.

## Highlights

- **First visit and first paint.** `KoraProvider` renders before `app.ready` (`waitForStorage` brings
  back the old gate), and hook writes made before the store opens are journaled. A first visit can
  read its first screen through the server (`sync.firstVisit.readThrough`, `POST <syncPath>/read`)
  while the local database fills. That read leaves from the first paint, before the code that handles
  its answer has downloaded, and a navigation's read holds back the store's own downloads for up to
  a second. A large first sync on browser OPFS is staged into a scratch replica and merged once, and the
  first paint's JavaScript is smaller (DevTools and protobufjs load only when used).
- **Kora Cloud from the CLI.** `kora deploy --platform kora-cloud`, `kora login`/`logout`/`whoami`,
  `kora export`/`import`, `kora deploy status`/`restart` and `.koraignore`.
- **Offline readiness.** `app.offline.status()` and `useOfflineReady()` report whether a reload with
  no network opens the app with its data (`ready` only when every part is proven; a part Kora cannot
  check reads `unknown`). Around it: durable writes on the IndexedDB fallback, storage-loss reporting,
  sign-in that restores offline, a service-worker shell status, `app.offline.keep()` for data and
  files, an `<OfflineBadge />` in every template, and `@korajs/test/playwright` plus a per-template
  offline suite (`pnpm test:e2e:offline`). [Offline Readiness](../guide/offline-readiness.md).
- **Access rules and sharing.** A schema can declare `access` (memberships, ordered roles, group
  collections) and per-collection read/write rules (`owner`, `member`, `memberOfKey`, `where`,
  `anyone`, `serverOnly`, `or`, `and`, `custom`). The sync server enforces them with no flag, follows
  membership changes in the download stream, gates history by membership interval, and honours
  capability grants (share links). New package `@korajs/spaces` adds invitations, roles, members,
  leaving and transferring on top. [Access Rules](../guide/access-rules.md),
  [Sharing](../guide/sharing.md).
- **Delivery visibility index (C2).** The server files each operation under the fields scopes use, so
  handshake, resume and live delivery read what a session can see instead of scanning the log. The
  session's filter stays the only authority on what it receives.
- **Faster device apply (C3, C3b).** A delivery batch is one storage transaction, at about one storage
  round trip per operation instead of about 18, with content ids verified before the transaction.
- **Version gate.** One build of an app writes a browser database at a time; a newer tab retires
  older ones with a reload prompt, without losing a confirmed write.
  [App updates and multiple tabs](../guide/app-updates.md).
- **Instant updates (opt in, off by default).** `createApp({ store: { instantUpdates: true } })` shows
  a tab's own writes in its live queries before the storage transaction commits, including
  transactions and atomic operations.
  [Instant Updates](../guide/instant-updates.md).
- **Tooling.** `kora upgrade`; `kora doctor --db` (preflight), `--dry-run-migrations`, `--production`
  (with a credential-free `--url` probe) and `--json`; one `src/schema.ts` in all 13 templates with a
  `schema-duplicates` check.

## Security and data safety

- **Previous values no longer leak across groups.** In an access-rules collection, an update that moves
  a record into a member's group no longer delivers the old group's content as `previousData`; every
  entry that differs from the new value is cut, or the update is withheld when the fold needs the
  base. An uploaded delete may carry no payload; `fieldVersions` and `foldState` are stripped from
  uploads.
- **A new member no longer receives what a record held before they could read it.** A scope entry's
  merge state sends removed array elements and deleted object keys only as a salted digest, and merges
  exactly as before. Richtext sends only the updates no newer one contains, with deleted text removed.
  Counters, atomic chains and custom-resolver logs are still sent, as is richtext deleted while
  another device saved a later edit without having seen the deletion (see "Current limits" in the access rules guide).
- **Access rules judge exactly the value the fold stores.** An insert carrying an atomic intent beside
  a different `data` value was judged as the default; updates are now judged on the record as the fold
  stores it (`INVALID_ATOMIC_OP` for malformed intents).
- **A record deleted while outside a device's view no longer comes back** through a stale write,
  on that device or a new one (`scopeExit: 'retain'`, retracted records, query-subset views, members
  who joined later). The beta.14 behaviour remains while a record's live-view summary is unknown.
- **Shared browsers.** Each account gets a device id, and so a sync node, of its own; before, two users'
  databases authored under one node and later servers refused all but the first
  (`DEVICE_OWNERSHIP_CONFLICT`). Writes of a retired node are re-authored under the account's node.
- **Capability grants** (share links) give a session a role in a group without a membership;
  `member(..., { grants: false })` requires a real membership. A deleted group grants its members
  nothing.
- **Server transactions decide on the active fold plan** during a rolling deploy, and changed
  transforms or merge rules re-fold records an older instance wrote.
- **Multi-tab storage.** A transaction span stays exclusive until its owner commits or rolls back; a
  follower's transaction is bound to the leader that answered its BEGIN; IndexedDB snapshots from two
  tabs cannot overwrite each other out of order; `ensureDurable()` cannot resolve for a lost write.
- **Restores.** A server replace-mode restore clears records and fold state in the transaction that
  replaces the log. A device's replace-mode `importBackup` records its unsynced writes in its own
  transaction, so a crash part-way no longer loses them.
- **Devices recover from any server restore**, including ones Kora never sees (`pg_restore`,
  point-in-time recovery, a copied SQLite file): each delivery batch carries a delivery anchor, and a
  server whose log differs there resyncs the device from 0.

- **Auth, server and desktop fixes that affect published beta.14** (admin authorization, org admin
  roles, TOTP atomicity, OAuth auto-linking, constant-time tokens, webhook DNS rebinding, request and
  session limits, backups, Tauri paths and identifiers, Lightsail secrets) are listed in the
  [beta.14 security advisory](./security-advisory-beta15.md).
- **Hardening of features new in this release:** a stale write is withheld when the server cannot
  tell where a deletion began; a `lastDeliverySequence: null` handshake no longer bypasses the
  access-rules history gate; anonymous read limits group IPv6 addresses by /64; causal heads follow a
  clock rebase, and rebase, rotation and re-author re-fold inside the rewriting transaction.

## Performance

Numbers from the changesets unless stated; each was measured on the host named there.

- Browser writes: 10,000 inserts in one transaction on OPFS, about 6.2 s to 1.8 s (Chromium); new OPFS
  databases use 16 KiB pages. `insertMany` of 10,000 records takes about 1.7 s
  (`docs/benchmarks/baseline.md`).
- Device apply: about 18 storage round trips per operation to about 1; first sync of a 20,000-operation
  school in Chromium on OPFS, about 6.4 minutes to about 2.3 minutes (the rest is OPFS journal I/O).
- Delivery index (`docs/design/fast-first-sync.md`, "C2 as built": a 100,000-operation log with
  20,000 visible, node, a shared host): the handshake and the first home row roughly 3 to 7 times
  faster and the full scope roughly 2 times, at the median. The per-run table behind it (SQLite,
  medians of 5; Slow 4G handshake 4.5 s to 1.3 s, full scope 16.9 s to 8.5 s with a wide spread) is
  in that document's history before #226, which says to read it "as a direction, not a magnitude".
- First-visit parity: on throttled 4G the first screen's read no longer waits for a code chunk (on a
  slow device the chunk now waits up to 300 ms for that read to leave, instead of racing it on a
  second connection), and a navigation's read no longer shares the link with the store's downloads;
  every cell of the parity benchmark passes, within the critical-path JavaScript budget (K3).
- First download from a remote database: owner edits no longer re-scope, and chunk reads are
  batched; delivery pauses at 2 MiB unacknowledged; a schema change re-folds only collections whose
  merge rules changed.
- Client: live-query registrations in a burst are batched (also while the stored sync positions
  are still loading); the outbound queue appends instead of
  re-sorting; staged apply yields the main thread every few milliseconds; a returning visit opens
  the database faster; the service-worker precache waits until after the first data.
- Startup re-materialization after a fold change is linear in the operation log (a 600-edit rich-text
  document: 1.5 s instead of 187 s) and resumable.

## Fixes

- Vue `KoraProvider` held the store in a deep `ref`, so the first `useQuery` result was discarded as
  stale after a reload (now `shallowRef`).
- The generated service worker looked up its precache with `Vary` in account, so a host sending
  `Vary: Origin` made an app that reported `ready` fail to open offline (lookups now ignore `Vary`).
  The offline shell also opens a folder's `index.html` for a path ending in `/`, and its update waits
  until no write is still committing before the page reloads.
- Blob pulls no longer hang on a lost message (retries, then `BlobTransferError`).
- A remote batch whose COMMIT answer was lost is published once instead of re-applied as duplicates.
- A follower tab no longer declares a live leader absent; a stopped sync engine stops its diagnostics
  interval; `SqliteServerStore.close()` and `PostgresServerStore.close()` no longer hang with nothing
  else alive (a regression in canaries since 20261024185231, never in a release).
- `createTestNetwork` no longer leaves its temporary directory behind.
- A first visit that goes offline before the runtime downloads no longer reloads the page into an
  error; it reloads once when back online. Closing the app while sync is starting no longer raises an
  unhandled `StoreNotOpenError`. A session ended with `SCOPE_CHANGED` reconnects without growing the
  backoff.
- `createKoraAuthSync` loads the stored session of an auth client nobody initialized (an app that used
  the client directly stayed signed out of sync after a restart); `OrgProvider` works under React
  StrictMode; `switchOrg` and `leaveOrg` have server routes; `ExternalJwtProvider` with `jwtSecret`
  accepts standard HS256 headers (with `kid`, without `typ`).
- One live query whose comparison fails no longer stalls the others in the same refresh;
  `AuthBoundKoraProvider` no longer leaves rejections unhandled; presence ids no longer collide and
  remote presence clears when the connection ends; the three server stores answer queries the same
  way; oversized bodies get `413`; the version gate releases its lock when opening fails; the
  IndexedDB durability barrier no longer gives up under steady writes; the DevTools overlay redraws
  only on new events; the blob access index sweeps expired sets in build order; a version gate closed
  or retired while opening keeps its rejection; a write queued behind a clock rebase, or behind one
  that fails to commit, never depends on a rewritten or rolled-back operation id; a json or object
  value with a key such as `toString` no longer makes `insert` throw; Vue
  `useRichText`/`usePresence` accept refs; Svelte rich text rebinds after
  `app.ready`; framework subpath exports and type declarations are complete (`korajs/react`
  re-exports all of `@korajs/react`).
- CLI: a Vite build that fails before writing its output shows its own error; `kora import` restores
  into a PostgreSQL server older than its client tools; `kora doctor` no longer warns about a
  self-contained script's schema, a conditional adapter choice or settings that merely end in `URL`;
  the Postgres stores no longer print "already exists, skipping" notices on every start.
  `kora deploy --platform aws-lightsail` forwards the settings `createProductionServer` and the blob
  store read from the environment (`KORA_INSIGHTS_TOKEN`, `KORA_ALLOWED_ORIGINS`,
  `KORA_BLOB_STORE_*`, `KORA_BLOB_DIR`); they were dropped, so files stayed on the container's disk.
- The insert type accepts `null` on an optional field with no default, as the runtime does; a
  required or defaulted field still refuses it at compile time.
- Instant updates: a write that has to read its record's base (while a write the overlay did not
  predict, such as an update that changes nothing, is changing that record) waits for the record's
  earlier writes to land. The read could miss a pending write, show the record without it until
  the commit, and report `store:overlay-diverged`.

## Deprecations kept

The `allowLegacyAnonymousClaims` default of `true` is still present and deprecated.

## Removed

Sync protocol 1 (Kora 1.0.0-beta.12 and earlier). Servers refuse those clients at the handshake
(`PROTOCOL_VERSION_UNSUPPORTED`). Operations they wrote keep their version-1 ids and stay valid.

The beta.12 merge pipeline: `experimental.legacyMerge`, `ExperimentalOptions`, and the deprecated
pairwise exports of `@korajs/merge`, including `MergeEngine` and `addWinsSet`. A database that ran
with the option re-materializes with the fold on its next open.

`store.sharedWorkerUrl` (and the `SqliteWasmAdapter` option of the same name), ignored since beta.6:
SharedWorker-hosted SQLite was never durable.
