# Kora.js 1.0.0-beta.15 (draft)

> **Draft. Not published.** Written from `main` at `0c1f8f3` against the tag `v1.0.0-beta.14`: the 72
> changesets added since beta.14 (`.changeset/*.md`, the ones not listed in `.changeset/pre.json`) and
> the 61 commits of `git log v1.0.0-beta.14..main`. The generated `CHANGELOG.md` files are written by
> Changesets when the "Version Packages" pull request is merged; this file is the narrative that goes
> with them. It must be re-checked against `main` on the day of the release. Section
> [Open items](#open-items-for-the-release) lists what is undecided or unbuilt.

**Behaviour-changing, not protocol-breaking.** The sync protocol stays at version 2 (new handshake
and delivery fields are optional). Upgrade every `korajs` and `@korajs/*` package together, **sync
servers first, then clients**. `npx kora upgrade` does the version bump and runs `kora doctor`.

- Upgrade guide: [Upgrading to beta.15](../guide/upgrading-to-beta15.md), with the change each item
  needs, a checklist, and what to monitor.
- Coming from beta.12 or beta.13: read [Upgrading to beta.13](../guide/upgrading-to-beta13.md) first.

```bash
npx kora upgrade --to 1.0.0-beta.15   # or: pnpm add korajs@1.0.0-beta.15 @korajs/server@1.0.0-beta.15 ...
npx create-kora-app@beta my-app       # new apps
```

Package versions of `create-kora-app` and `@korajs/tauri`, and the template pins, are set by the
release PR and are filled in here at release time.

## Highlights

- **Offline readiness.** `app.offline.status()` and `useOfflineReady()` report whether a reload with
  no network opens the app with its data (`ready` only when every part is proven; a part Kora cannot
  check reads `unknown`). Around it: durable writes on the IndexedDB fallback, storage-loss reporting,
  sign-in that restores offline, a service-worker shell status, `app.offline.keep()` for data and
  files, an `<OfflineBadge />` in every template, and `@korajs/test/playwright` plus a per-template
  offline suite (`pnpm test:e2e:offline`). [Offline Readiness](../guide/offline-readiness.md).
- **Access rules and sharing.** A schema can declare `access` (memberships, ordered roles, group
  collections) and per-collection read/write rules (`owner`, `member`, `memberOfKey`, `where`,
  `anyone`, `serverOnly`, `or`, `and`, `custom`). The sync server enforces them with no flag, follows
  membership changes in the download stream, gates history by membership interval, and honours
  capability grants (share links). New package `@korajs/spaces` adds invitations, roles, members,
  leaving and transferring on top. [Access Rules](../guide/access-rules.md),
  [Sharing](../guide/sharing.md).
- **Delivery visibility index (C2).** The server files each operation under the fields scopes use, so
  handshake, resume and live delivery read what a session can see instead of scanning the log. The
  session's filter stays the only authority on what it receives.
- **Faster device apply (C3, C3b).** A delivery batch is one storage transaction, at about one storage
  round trip per operation instead of about 18, with content ids verified before the transaction.
- **Version gate.** One build of an app writes a browser database at a time; a newer tab retires
  older ones with a reload prompt, without losing a confirmed write.
  [App updates and multiple tabs](../guide/app-updates.md).
- **Instant updates (opt in, off by default).** `createApp({ store: { instantUpdates: true } })` shows
  a tab's own writes in its live queries before the storage transaction commits.
  [Instant Updates](../guide/instant-updates.md).
- **Tooling.** `kora upgrade`; `kora doctor --db` (preflight), `--dry-run-migrations`, `--production`
  (with a credential-free `--url` probe) and `--json`; one `src/schema.ts` in all 13 templates with a
  `schema-duplicates` check.

## Breaking and behaviour-changing

Each item has its code change in the [upgrade guide](../guide/upgrading-to-beta15.md).

| Change | Affects |
|---|---|
| A custom `AuthTokenStorage` without `durability` reads as `unknown` and is never offline-`ready`; an app with a bare `sync.auth` function reads `not-ready` until it declares `offline.auth`. | Custom token stores; own sign-in |
| A custom `ContentAddressedBlobStore` without `durable` counts as not durable (`storage-non-durable` for a pin that keeps files). The member is optional. | Custom blob stores |
| On the IndexedDB fallback a write waits for a snapshot that holds it and can reject with `WriteNotDurableError` (`WRITE_NOT_DURABLE`); the write exists, do not retry it. | Apps on the IndexedDB fallback |
| Update `korajs`, `@korajs/auth` and `@korajs/cli` together, or offline status reads `auth-unknown` / `shell-none` and is never `ready`. | Everyone |
| `offline` and `reloadForNewBuild` are reserved app property names. | Collections with those names |
| Version gate: older tabs retire with `BuildSupersededError`; close old tabs once after the first beta.15 deployment; `app.close()` can be refused (`UNSAVED_WRITES`); the gate is off on plain HTTP; a browser without Web Locks on HTTPS rejects `app.ready` (`TabCoordinationUnavailableError`, `allowUncoordinatedTabs` for tests). | Browser apps |
| `koraServiceWorker()` stamps a `kora-build` meta tag into built pages (`buildId: false` opts out). | Vite apps |
| The default `spaFallback` is `'navigation'`: crawlers asking `*/*` get the app shell for extensionless routes; `'strict'` keeps the beta.14 behaviour. | `createProductionServer` |
| An uploaded delete with `data`, `previousData` or `atomicOps` is refused `INVALID_DELETE_PAYLOAD`; malformed atomic intents are refused `INVALID_ATOMIC_OP`. | Custom clients |
| Scope grants: a predicate object other than exactly `{ $in: [...] }` is refused at the handshake (`SCOPE_PREDICATE_LIMIT`); a `null` or non-object collection grant denies the collection. `$or` grants are new, and refuse a beta.14 client (`CLIENT_TOO_OLD`). | Custom `AuthProvider`s |
| A schema that declares `access` is always enforced; a client that cannot follow it is refused `CLIENT_TOO_OLD`; a store without the membership index is refused `ACCESS_RULES_UNSUPPORTED_STORE`; a collection that relied on field rules alone to admit inserts now needs a `create` rule. `experimentalAccessRules` is a deprecated no-op. | Apps adopting access rules |
| Retractions apply in stream order within a batch; an insert onto an existing record enters and leaves a view like an update. `forceFullResync` repairs devices that already hold a wrongly kept record. | Scoped apps |
| `kora.applyConditional` is one transaction on every built-in store; on Postgres it now runs the schema, constraint and relation checks it skipped. | Server routes |
| `PasswordResetManager` and `EmailVerificationManager` take `(userStore, { url, send, ... })`; the old options and error classes are removed; a custom `UserStore` needs `updatePasswordIf`; `UserStore.update()` writes the profile only. | Code that built these managers |
| `SqliteServerStore.close()` closes the connection `createSqliteServerStore` opened. | Scripts and tests |
| Blob pull failures reject with `BlobTransferError` (was a plain `Error`); `timeoutMs` is a deprecated alias of `deadlineMs`; `BlobChunkChannel.send` returns a boolean. | Blob users, custom channels |
| `@korajs/cli/create` is ESM only (no `require` condition). | CommonJS code that required it |
| Native SQLite uses `synchronous = FULL`. | Node and Tauri apps |

## Security and data safety

- **Previous values no longer leak across groups.** In an access-rules collection, an update that moves
  a record into a member's group no longer delivers the old group's content as `previousData`; every
  entry that differs from the new value is cut, or the update is withheld when the fold needs the
  base. An uploaded delete may carry no payload; `fieldVersions` and `foldState` are stripped from
  uploads.
- **Access rules judge exactly the value the fold stores.** An insert carrying an atomic intent beside
  a different `data` value was judged as the default; updates are now judged on the record as the fold
  stores it (`INVALID_ATOMIC_OP` for malformed intents).
- **A record deleted while outside a device's view no longer comes back** through a stale write,
  on that device or a new one (`scopeExit: 'retain'`, retracted records, query-subset views, members
  who joined later). The beta.14 behaviour remains while a record's live-view summary is unknown.
- **Shared browsers.** Each account gets a device id, and so a sync node, of its own; before, two users'
  databases authored under one node and later servers refused all but the first
  (`DEVICE_OWNERSHIP_CONFLICT`). Writes of a retired node are re-authored under the account's node.
- **Capability grants** (share links) give a session a role in a group without a membership;
  `member(..., { grants: false })` requires a real membership. A deleted group grants its members
  nothing.
- **Server transactions decide on the active fold plan** during a rolling deploy, and changed
  transforms or merge rules re-fold records an older instance wrote.
- **Multi-tab storage.** A transaction span stays exclusive until its owner commits or rolls back; a
  follower's transaction is bound to the leader that answered its BEGIN; IndexedDB snapshots from two
  tabs cannot overwrite each other out of order; `ensureDurable()` cannot resolve for a lost write.
- **A replace-mode restore** clears records and fold state in the transaction that replaces the log.

Whether any of these needs a security advisory is an [open item](#open-items-for-the-release).

## Performance

Numbers from the changesets unless stated; each was measured on the host named there.

- Browser writes: 10,000 inserts in one transaction on OPFS, about 6.2 s to 1.8 s (Chromium); new OPFS
  databases use 16 KiB pages. `insertMany` of 10,000 records takes about 1.7 s.
- Device apply: about 18 storage round trips per operation to about 1; first sync of a 20,000-operation
  school in Chromium on OPFS, about 6.4 minutes to about 2.3 minutes (the rest is OPFS journal I/O).
- Delivery index (`docs/design/fast-first-sync.md`, "C2 as built"; SQLite, node, a shared 2-core
  container, medians of 5, "a direction, not a magnitude"): Slow 4G handshake 4.5 s to 1.3 s, first home
  row 4.6 s to 1.3 s, full scope 16.9 s to 8.5 s (wide spread).
- Startup re-materialization after a fold change is linear in the operation log (a 600-edit rich-text
  document: 1.5 s instead of 187 s) and resumable.

## Also new

`app.<collection>.insertMany`; `useMutation(..., { onRejected })` and a `rejected` state (React, Vue,
Svelte); `exportLocalDatabase()`; `onOperationsCommitted` and `kora.transaction` on the sync server;
`server.access` (`grant`, `revoke`, `transfer`, `backfill`, `roleOf`); `forceFullResync` on the
production server; `shellMeta` for per-URL link previews; password reset, change and email
verification in `@korajs/auth`; `useFormDraft`; protocol-1 session counters in `/__kora/status` and
`/__kora/metrics`; `/health` fields `authRequired` and `protocolVersion`.

## Fixes

- Vue `KoraProvider` held the store in a deep `ref`, so the first `useQuery` result was discarded as
  stale after a reload (now `shallowRef`).
- The generated service worker looked up its precache with `Vary` in account, so a host sending
  `Vary: Origin` made an app that reported `ready` fail to open offline (lookups now ignore `Vary`).
- Blob pulls no longer hang on a lost message (retries, then `BlobTransferError`).
- A remote batch whose COMMIT answer was lost is published once instead of re-applied as duplicates.
- A follower tab no longer declares a live leader absent; a stopped sync engine stops its diagnostics
  interval; `SqliteServerStore.close()` and `PostgresServerStore.close()` no longer hang with nothing
  else alive (a regression in canaries since 20261024185231, never in a release).
- `createTestNetwork` no longer leaves its temporary directory behind.

## Deprecations kept

Protocol 1 (beta.12 clients), `experimental.legacyMerge` and the `allowLegacyAnonymousClaims` default
of `true` are present in `main` at `0c1f8f3` and still deprecated. The server counts protocol-1
sessions so the removal can be judged.

## Open items for the release

These are unresolved in this draft. None is decided here.

1. **Protocol-1 removal timing (decision 6 in `docs/plans/beta15-dogfood-consolidated-plan.md`; Obed
   decides).** Removal of protocol 1, `legacyMerge` and `allowLegacyAnonymousClaims: true` was promised
   for "a later release" (section E of the plan). The plan's gate is two weeks of zero
   `session.protocol_deprecated` events in koraforms, koradocs and the LMS; the clock for koraforms and
   koradocs started 2026-10-21 (earliest 2026-11-04) and the LMS clock cannot start until the LMS runs
   protocol 2 and every learner device has updated. The plan records a recommendation and states that
   moving the removal out of beta.15 is a re-scope that needs an explicit decision. Until it is
   decided, these notes and the upgrade guide say only that the three are still present and
   deprecated, and `CLAUDE.md` keeps its protocol line (a human edit when removal ships).
2. **Security advisory.** The plan says security and data-loss fixes ship in beta.15. No advisory draft
   exists for this release. Which fixes above (previous-value gating, out-of-view delete, shared-browser
   node identity, atomic-intent rule bypass) affect published beta.14 deployments, rather than only
   canaries or access rules that are new in this release, has not been established here.
3. **Cold start from current state (C1).** In the plan's beta.15 scope (decision of 2026-10-28), not on
   `main` at `0c1f8f3` (only its preconditions: batch verification, the Chromium measurement, the
   design re-review). These notes make no cold-start claim.
4. **Other plan items listed as outstanding and not re-verified for this draft:** `@korajs/spaces` npm
   `latest` dist-tag; npm trusted publishing (D9); C4 published benchmark results and bundle budgets;
   the remaining packed-artifact matrix; koraforms v22; the LMS on a canary in production; two weeks of
   release-candidate use in koraforms and koradocs; the external security review; the competitive
   bake-off; an archived green release record. Instant updates ship **off by default**; flipping the
   default needs a dogfood week with zero `store:overlay-diverged`.
5. **Docs gap.** `deliveryPartitions` and `delivery.partition_miss` are documented only in the
   upgrade guide and the TypeScript doc comments; the production server guide has no section on the
   delivery index.
6. **Rollback.** A server or client that ran beta.15 and is then returned to beta.14 on the same
   database has not been tested.
